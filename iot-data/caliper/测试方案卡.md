# iot-data 链码性能测试方案卡（Caliper）

> 版本：v1.0　制定日期：2026-10-19
> **制定原则：通过标准（阈值）先于测试制定。** 测试结果只与下表阈值比对判定通过/不通过，不以“跑出来多少就定多少”倒推标准。

---

## 1. 测试目标

对 iot-data 链码（`chaincode-go/chaincode/smartcontract.go` v2.0，含 ECDSA 验签、确定性时间戳、授权校验）在 Hyperledger Fabric 2.2 测试网上进行性能基准测试，量化：

- **吞吐（TPS）**：写类（`ReportData` / `RegisterDevice`）与读类（`GetDeviceData`）交易的每秒成功提交量；
- **端到端延迟**：交易从提交到被确认（背书 + 排序 + 提交 + 事件）的时延分布；
- **稳定性**：无失败交易、无超时、无共识分歧。

结论仅用于确认修复后的链码在性能上满足验收要求，不对外宣称绝对性能。

## 2. 被测系统（SUT）

| 项目 | 取值 |
|---|---|
| 平台 | Hyperledger Fabric v2.2.0（test-network） |

## 3. 测试场景（Scenarios）

每个场景先做**预置（setup）**：批量注册并激活 N 台设备，把授权/上报所需的密钥与签名材料备好，使基准阶段只测目标交易、不含预置开销。

| 场景 | 目标函数 | 类型 | 背书 | 内容 |
|---|---|---|---|---|
| **S1 数据上链** | `ReportData` | 写 | 2 peer（MAJORITY） | 设备直连上报数据（含 ECDSA 验签），核心 IoT 写路径 |
| **S2 设备注册** | `RegisterDevice` | 写 | 2 peer（MAJORITY） | 设备注册生命周期入口 |
| **S3 数据查询** | `GetDeviceData` | 读 | 单 peer | 所有者/被授权方按设备查询上报数据 |
| **S4 混合负载** | `ReportData` + `GetDeviceData` | 混合 | 写 2 peer / 读 1 peer | 读写比 8:2，模拟真实“上报为主、查询为辅” |

> 说明：`ReportData` 的 ECDSA 验签在**背书阶段**执行，是 S1/S4 的关键成本项，因此单独列为 S1 并与 S2（无验签写）对照。

---

## 4. 指标定义（Metrics）

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **TPS** | 每秒成功提交（committed）的交易数 = 成功交易数 / 观测时长 | Caliper 报告 |
| **延迟** | 交易从提交到被确认的端到端时延，报 min / avg / P50 / P95 / P99 | Caliper 报告 |
| **成功率** | 成功交易数 / 总交易数（目标 100%，任何 error/timeout 即失败） | Caliper 报告 |
| **资源占用** | peer0.org1 / peer0.org2 / orderer 容器 CPU% 与内存（辅助，不计入判定） | `docker stats` 采样 |

延迟统计口径：**仅统计成功交易**；失败的请求单独计入成功率，不计入延迟分布。

---

## 5. 通过标准（Pass Criteria）——先于测试制定

> 判定规则：**任一场景的任一指标不满足即该场景不通过；四个场景全部通过 → 性能验收通过。**

| 场景 | 成功率 | TPS（下限） | 平均延迟（上限） | P99 延迟（上限） |
|---|---|---|---|---|
| S1 数据上链 | = 100% | ≥ 10 | ≤ 3000 ms | ≤ 8000 ms |
| S2 设备注册 | = 100% | ≥ 10 | ≤ 3000 ms | ≤ 8000 ms |
| S3 数据查询 | = 100% | ≥ 50 | ≤ 1000 ms | ≤ 3000 ms |
| S4 混合负载 | = 100% | ≥ 20 | ≤ 3000 ms | ≤ 8000 ms |

**阈值制定依据**（记录在案，防止事后改标准）：
- 写类（S1/S2/S4）按 MAJORITY 背书（2 peer）+ 排序 + 提交 + 单机资源争用，下限定 **10 TPS** 为可稳定达成的最低可接受吞吐；S4 因含读放大到 **20 TPS**。
- 读类（S3）仅单 peer 背书、无排序，下限定 **50 TPS**。
- 延迟上限为单机场景的宽松安全线，主要用于拦“接近超时/共识卡死”的异常，不作为性能调优目标。
- 成功率一律 **100%**：验收功能已包含负向用例，性能测试不允许出现功能性的失败/超时。

## 7. 工作量与配置要点（后续实现，不在本卡判定范围）

1. **Caliper 工程结构**（本目录 `caliper/` 下补齐）：
   - `networks/networkConfig.json`：connection profile 指向 org1 + org2 两个 peer（`localhost:7051` / `localhost:9051`，TLS 证书路径与 `env.sh` 一致）；
   - `benchmarks/config.yaml`：每个场景一个 round，`rateControl` 用 `fixed-rate` 或 `fixed-feedback-rate` 逐轮加压找 TPS 上限；
   - `workload/iotdata-workload.js`：实现 S1~S4 的 submit/query 参数生成。
2. **签名要求（关键）**：S1/S4 的 `ReportData` 必须携带**每台设备私钥对 `deviceID|dataType|value|rawTimestamp` 的 ECDSA(P-256) 签名**，输出 `hex(r||s)` 64 字节（与链码 `verifyReportSignature` 一致）。工作负载模块需为每台设备预生成密钥并在线签名（Node `crypto` 或 `elliptic`；注意 Node 原生 ECDSA 输出 DER，需转 r||s）。
3. **预置规模**：N = 100 台设备（先小规模验证），注册→激活完成；查询场景每台设备预置若干条 `ReportData` 记录。
4. **预热与稳态**：正式统计前短预热，避免首个块/容器冷启动计入延迟。
5. **结果证据**：保存 Caliper `report.html` 与 `docker stats` 采样，与本卡阈值逐项比对输出“通过/不通过”结论。
